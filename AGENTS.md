# Agentic Gate Project Guide

## Vision

Agentic Gate is the control point between code generated by a coding agent and code accepted by a project.

Coding agents should receive quality feedback inside the edit loop, while the changed code and task context are still fresh. Every supported ecosystem should expose the same outcome even when its native tools differ: run the relevant checks, enforce the project's hard quality boundary, and return failures in a form an agent can locate, repair, and verify.

## Mission

Agentic Gate provides continuous code quality for coding agents through three responsibilities:

1. **Check** — run linting, static analysis, complexity checks, tests, and project-wide analysis after changes or compilation.
2. **Enforce** — decide whether the current result may proceed. Gate checks produce `pass` or `block`; they are not advisory warnings.
3. **Feedback** — normalize every failure into an actionable violation that explains what failed, where it failed, why it matters, how to repair it, and how to verify the repair.

Build on mature ecosystem tools where their analysis scope fits. Add Agentic Gate rules where the project needs a distinct hard policy or analysis across files, modules, or the whole project. Do not reimplement a mature file-local rule merely to put the Agentic Gate name on it.

The current product priorities are:

- make `agentic-gate-cli` the JavaScript/TypeScript composition root and public runner;
- compose the project's complete ESLint configuration, curated third-party hard gates, and Agentic Gate's own checks in one run;
- keep policy definitions in `agentic-gate-rules` and execution control in `agentic-gate-engine`;
- make the gate enforce itself before accepting changes; and
- enforce Java and Kotlin through the JVM lint engine and the Gradle post-compilation lifecycle.

## Product Contract

- A run returns `pass` only when it has no violations; one or more violations return `block`.
- Every finding exposed by the product is a `Violation`.
- Every violation has a stable check ID, a message, a truthful source location, analyzer evidence, and remediation containing both an instruction and a verification step.
- Locations use `file`, plus optional `start` and `end` positions shaped as `{ line, column }`.
- Analyzer-specific details stay in `evidence`; callers should not need analyzer-specific result types.
- Project configuration uses `gate.config.{ts,mts,js,mjs}`. ESLint continues to use the project's `eslint.config.*`.
- Every gate check is a blocking error. Rule behavior, thresholds, severities, exceptions, and disable switches are not configurable.

## Architecture

### Name by responsibility

Names must describe a stable domain responsibility and abstraction boundary. Do not name a product module after a replaceable implementation technology.

- `jvm/engine` owns JVM analysis flow. It uses Android Lint and UAST internally to analyze Java and Kotlin, invokes injected rules, and does not expose those implementation technologies in the module name.
- `jvm/gradle` owns the JVM composition root and Gradle lifecycle integration.
- `jvm/rules` owns concrete JVM quality policies.
- `es/cli` owns the ES composition root, public runner, configuration loading, output, and process lifecycle.
- `es/rules` owns native policies, ESLint plugin assembly, and the curated Unicorn gate.
- `es/engine` owns contracts, project discovery, analyzer execution, gate decisions, and result normalization.
- Do not use `integration` or `integrations` as a generic production-code bucket. Name production code for the capability it provides.
- Do not use `scripts` as a miscellaneous source-code bucket. Repository-wide tooling belongs under `tooling`, and a single-purpose tool should normally be a named file such as `tooling/docs.ts`. Project-specific build logic belongs to that project, such as `es/cli/build.ts`.

Expose an implementation technology in a package or module name only when integrating with that technology is the module's public contract. A private dependency on ESLint, Unicorn, Android Lint, UAST, TypeDoc, or Dokka is not by itself a naming boundary.

### Platform boundaries

- Platform implementations live under `es/` and `jvm/`.
- JavaScript/TypeScript production code is TypeScript, targets Bun, and uses strict TypeScript settings.
- Relative imports in TypeScript name the actual `.ts` or `.tsx` source file. TypeScript rewrites those extensions for emitted JavaScript; source code must not hard-code the output `.js` filename.
- The published `agentic-gate-cli` command is a standalone executable built with Bun compile and minification. Keep JavaScript and declaration output for its programmatic API, and execute the binary against a real fixture during CI.
- The npm packages are `agentic-gate-cli`, `agentic-gate-rules`, and `agentic-gate-engine`; the executable is `agentic-gate-cli`.
- A project may directly reference only files it owns. Cross-project source usage goes through the dependency package name and its public build artifacts; member-package scripts must not escape their project directory, and package exports must not expose source files.
- Project-wide ES analysis belongs to the engine rather than being forced into an ESLint plugin.
- JVM code must not depend on ES implementation types. Shared behavior is a platform-neutral contract implemented by each platform.

### ES project structure

- `es/cli/src/runner.ts` is the composition root. It loads project configuration and concrete rules, injects them into the engine, and exposes `runGate`.
- `es/cli` depends on `es/rules` and `es/engine`. Neither package may depend on the CLI.
- Stable configuration, result, rule identity, and violation contracts live in `es/engine/src/contract/`.
- Project discovery, parsing, dependency resolution, analyzer execution, gate sequencing, decisions, and result assembly live in `es/engine/`.
- File-local ESLint rules live in `es/rules/src/rules/unit/`; cross-file and project-wide policies live in `es/rules/src/rules/global/`.
- ESLint plugin assembly and presets live in `es/rules/src/eslint/`.
- `es/rules` depends only on the engine's public package interface. The engine must never import concrete rules.
- A public index may aggregate real modules. It must not hide an otherwise unnecessary one-file directory.

Keep the distinction between `unit` and `global` semantic: a unit rule can decide from one ESLint source file; a global rule needs project files, module relationships, package metadata, or a graph.

Each `package.json` or Gradle project is an architecture boundary. Project manifests declare the dependency direction; do not duplicate that structure in `gate.config.ts`. The top-level runner loads concrete rules and injects them into the engine. The engine controls the execution flow through rule contracts and IoC without importing the rules project. `agentic-gate/no-module-dependency-cycles` keeps each source graph acyclic.

### Layered architecture gate

For an ES workspace, the root `package.json` is the architecture-analysis entry point. Its `workspaces` field defines the complete set of project nodes. Self-gating runs once from that root and analyzes the workspace as one graph; it must not evaluate the CLI, rules, and engine projects as unrelated runs.

A workspace package is one architecture layer node. The gate does not accept a separately configured numeric layer list. The package graph is a partial order, not a fixed chain: a direct dependency may skip topological ranks when the caller genuinely uses the callee's public contract. Two packages are peers only when neither depends on the other.

Layer division is structurally valid only when all of these conditions hold:

- every production source file belongs to exactly one workspace package, determined by its nearest owning `package.json`;
- every production file is reachable from that package's public entries;
- code outside a package reaches it through its package name and declared `exports`, never through a relative path or an internal source path; and
- a directory module and a workspace package both hide their implementation behind their declared interface.

Layer relationships are valid only when all of these conditions hold:

- every cross-package source import has a matching direct dependency in the caller's manifest;
- runtime source imports require `dependencies`, `optionalDependencies`, or `peerDependencies`; `devDependencies` authorize only type-only imports and build tooling;
- every imported package subpath is explicitly public in the callee's `exports`;
- the workspace package dependency graph is acyclic;
- static source dependencies point from the composition root and policy packages toward engine contracts and lower capabilities; and
- concrete policy selection and object construction happen in the composition root. An engine invokes injected policies at runtime but never imports their concrete package.

Static dependency direction and runtime call direction are different graphs. In this repository, the required static graph is `cli -> rules`, `cli -> engine`, and `rules -> engine`. At runtime, the CLI creates the rules, passes them to the engine, and the engine calls those injected rules. The runtime callback does not authorize an `engine -> rules` source dependency.

The architecture gate blocks undeclared workspace dependencies, relative imports across package boundaries, imports of unexported package internals, package dependency cycles, and source dependencies from the engine back to concrete rules or the CLI. Structural analysis cannot infer whether a business responsibility was named well or whether a forwarding package has business value; it enforces the boundaries and dependency direction that source and manifests prove.

### Source modules and interfaces

A `package.json` defines a package/project boundary. Within a source tree, use these interface rules:

- A named source file such as `config.ts` is a single-file interface.
- A directory is a module only when its `index.{ts,tsx,js,jsx,mjs,cjs}` fronts additional implementation files or child modules.
- Do not create a directory containing only `index.*` to satisfy a structural rule. Replace it with a named source file.
- External callers import a directory module through the directory path. Do not spell `index` explicitly.
- External callers must not import implementation files or traverse through a module into its nested modules.
- A package export exposes a real module index. It must not expose a directory module's implementation file or an individual internal source file.
- Module-name analysis must distinguish conceptual affinity, lexical similarity, and token-boundary similarity. Do not collapse them into one score or enforce them with one heuristic gate.

Design the interface first. A structural rule should reveal weak boundaries, not encourage ceremonial directories or forwarding indexes.

## Rule Conventions

### Identity and registration

- Every native rule filename uses `no-kebab-case.ts` and is the single source of truth for its public name and `agentic-gate/<name>` ID.
- Define rules with `defineRule(import.meta.url, ...)` or `defineProjectRule(import.meta.url, ...)` and export the result directly.
- Registries derive their keys from rule metadata. Do not repeat the filename as a hard-coded registry key, rule ID, or semantically identical variable name.
- ESLint message IDs come from the keys of `meta.messages`. Do not duplicate them in a separate enum.
- Every violation must be proven directly from source syntax, an AST, a resolved dependency graph, or an explicit project contract. Do not infer intent, conceptual identity, ownership, handling, or architectural responsibility from names, lexical overlap, similarity scores, arbitrary cutoffs, or incomplete parsing.
- Duplication means either identical content or identical behavior. Content identity is exact equality after removing representation-only syntax such as source locations and comments. Behavioral identity must be established by an explicit semantics-preserving normalization; resemblance is not evidence of duplication. Because general program equivalence is undecidable, a duplication rule may report only the subset it can prove and must not guess at the rest.
- Consecutive means two or more adjacent occurrences in the same ordered syntax sequence. Two is the definition boundary, not a configurable threshold.
- Hard rules have no configurable behavior, thresholds, severity, disable switch, allowlist, or exception list. `gate.config.ts` may describe project discovery inputs, never negotiate whether a violation counts.
- The numeric values -1, 0, and 1 are structural algorithm values rather than magic numbers: they express predecessor or absence, the zero element or first position, and one-step progression. This fixed semantic definition is part of the rule, not a configurable allowlist.
- Other numeric literals are considered named when they initialize a `const`, enum member, readonly field, statically named object field, or JSX attribute. Computed member indexes are executable expressions and remain subject to the rule.
- An unsupported or ambiguous analysis input fails explicitly. It must never select the first candidate, invent missing evidence, or silently skip a file.

### Scope and reuse

- Prefer an established ESLint plugin for a mature file-local check. Curate individual high-confidence gate rules; do not import a plugin's `recommended` preset wholesale.
- All configured ESLint plugins participate in the CLI run. Overlay configurations in order and promote warnings to blocking errors.
- Agentic Gate owns rules that express its specific policy or require cross-file knowledge.
- Reuse an existing constant within the same directory module instead of defining an equivalent constant again. Different directory modules are not required to share constants.
- Constant objects declared with `as const` use a PascalCase binding and UPPER_SNAKE_CASE keys.

Preserve these established global-rule semantics unless a deliberate product change updates code, tests, and documentation together:

- duplicated-statement analysis compares complete top-level statements within one file or across files; an isolated expression is not a comparison unit;
- duplicated-function analysis compares complete function implementations within one file or across files, excluding only the declared function name;
- declaration identity matters for top-level declarations, so `const A = 1` and `const B = 1` are not duplicates, while repeated `const A = 1` declarations are;
- repeated template-literal analysis compares exact word-bearing fragments from template strings and reports two or more occurrences; a fragment is word-bearing when it contains a Unicode letter, mark, number, or connector punctuation character, while pure punctuation and whitespace are excluded;
- duplicate constants are enforced within the same directory module, not across unrelated modules;
- unused-file and unused-export analysis treats valid `package.json` exports as public entry points; and
- module-boundary analysis enforces the interface rules in this document.
- module-dependency analysis rejects every source cycle so the graph always has a topological direction from upper modules to lower modules.

### Actionable feedback

A new rule is incomplete until its violation tells an agent how to fix and verify the problem. Messages should identify the concrete offender. Remediation should prescribe a change rather than restate the rule. Locations must be as precise as the analyzer can truthfully provide; never invent a line or column for a file-level finding.

## Documentation

Source comments are the canonical developer documentation for rules and public contracts.

- Document each ES rule in its source with TSDoc. TypeDoc generates the ES HTML site.
- Document Kotlin rules and public contracts with KDoc. Dokka generates each JVM module's HTML site.
- Each gate owns an independent generated site and declares it through `docs.manifest.json`.
- The root documentation assembler consumes generated static sites and publishes the combined portal under `docs/`.
- Keep hand-written README material focused on product usage, architecture, and navigation. Do not maintain a second prose copy of rule behavior that can drift from the source.
- Update English `README.md` and Chinese `README.zh.md` together when shared content changes. English is the default README.
- Describe current implementation truthfully. Planned or scaffold-only behavior must be labeled as such.

Generated documentation is build output. Change the source comments or generator rather than hand-editing generated HTML.

## Testing and Verification

Agentic Gate must gate its own source.

- During implementation, run the narrowest meaningful test that proves the changed behavior.
- Before reporting an ES or repository-wide change complete, run `bun run ci` from the repository root.
- `bun run gate:self` is defined only at the workspace root. It starts from the root `package.json` and evaluates all ES workspace projects in one run so cross-project architecture remains visible; individual package checks must not run isolated self-gates.
- `bun run ci` covers type checking, unit and project tests, the self-gate, build, built-package smoke validation, Gradle TestKit, local Maven publications, TypeDoc, Dokka, aggregate documentation, Knip, and the runnable example.
- Add fixtures for project-wide behavior and focused RuleTester cases for file-local ESLint behavior.
- Tests should prove externally meaningful behavior and important failure modes. Do not add tests that merely repeat an implementation detail.
- Built-artifact validation belongs under `smoke/`; it is neither production tooling nor an ordinary source-level unit test.
- For JVM changes, run `bun run check:jvm`; it executes the Gradle checks and publishes the artifacts to Maven Local. The Java example then resolves the plugin marker, implementation, engine, and rules from that local repository.
- Run `git diff --check` and search for stale names or paths after renames.

## CI and Release

- `.github/workflows/ci.yml` runs `bun run ci` for every new pull-request revision targeting `main`.
- Keep the required CI job name `Build and test` stable unless repository protection is updated with it.
- Releases are triggered by version tags in the form `1.2.3` or `v1.2.3`, optionally followed by a prerelease suffix.
- A version containing `-` is a prerelease, publishes to npm with the `next` tag, and creates a GitHub prerelease.
- A version without `-` is a stable release and publishes with the npm `latest` tag.
- The release tag is the source of the npm package version. Do not manually maintain a release-only version change before tagging.
- Publish the ES packages in dependency order: `agentic-gate-engine`, `agentic-gate-rules`, then `agentic-gate-cli`. Rewrite internal workspace dependencies to the tag version before publishing.
- npm publishing uses `NPM_TOKEN`. Maven Central publishing uses `GPG_KEY_ARMOR`, `GPG_KEY_ID`, `GPG_PASSPHRASE`, `OSSRH_PACKAGE_GROUP`, `OSSRH_USERNAME`, and `OSSRH_PASSWORD`. Every release runs the complete CI command before publication.
- Publish `jvm/engine`, `jvm/rules`, the Gradle plugin implementation, and its plugin marker to Maven Central with `io.johnsonlee.sonatype-publish-plugin`. The release tag supplies their Gradle version.

## Change Discipline

- Preserve one coherent architectural story across code, tests, documentation, examples, build files, and workflow files.
- Search all downstream references before renaming a file, field, rule, package, module, command, or public concept.
- Prefer removing duplication at its source over introducing mappings, aliases, or hard-coded translation tables.
- Reuse established constants and public contracts within their module scope.
- Do not add abstractions, directories, configuration, or compatibility layers without a present use case.
- Do not claim a planned capability is implemented.
- Keep feature pull requests focused and reviewable. When the branch is intentionally maintained as one commit, amend that commit and update the remote with `--force-with-lease` rather than adding cleanup commits.
- Do not stop at a partial result when the remaining work is authorized and can be completed safely.

When code and this guide disagree, determine whether the implementation drifted or the documented decision changed. Fix the false side and update every dependent artifact in the same change.
